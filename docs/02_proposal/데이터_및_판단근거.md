## 2. 장소 점수 — 왜 이 장소인가 (`tools/places.py`, `config/settings.json`)

```
점수 = w1 × 관심사 + w2 × 분산(563) + w3 × 한적함(1208)
기본 (w1, w2, w3) = (0.6, 0.2, 0.2) · 한적함 요청 시 (0.4, 0.3, 0.3)
```

| 항 | 계산 | 의미 |
|---|---|---|
| 관심사 | 장소 분류가 관심사 분류 목록(`interests.json`)에 있으면 1, 없으면 0. 관심사 미입력(또는 음식·카페만)이면 분류 있는 장소 1, 분류 없음 0.5 | 원하는 종류의 장소 |
| 분산 | 1 − (장소가 속한 읍면동의 방문/거주 비율 백분위) | 사는 사람 대비 찾는 사람이 적은 동일수록 높음 |
| 한적함 | 1 − (장소 반경 1km 렌터카 체류 수 백분위) | 주변에 렌터카가 덜 머무는 곳일수록 높음 |

- 여행 월을 입력하면 563의 그 달 값을, 없으면 연평균을 쓴다.
- 지표가 없으면 0.5(중립)로 계산하고 화면에 "지표 없음"으로 표시한다.
- 점수가 같으면 `place_id` 순. **같은 데이터 버전 + 같은 설정 + 같은 조건 → 같은 순위**(재현성).
- 한적함 요청("조용한·한적한·덜 붐비는…")은 가중치를 바꿔 허브 데이터가 순위를 더 크게 움직이게 한다 → 필수 데이터가 판단을 바꾸는 시연 지점.
- 표시 원칙: 563은 "{행정동} 지표 (읍면동 단위)", 1208은 "장소 반경 1km 지표"로 분리 표시. 읍면동 통계를 장소의 혼잡도로 표현하지 않는다.

## 3. 경로 생성 (`tools/itinerary.py`)

1. 하루 장소 수 k: 여유롭게 3 · 보통 4(기본) · 빡빡하게 5.
2. 권역 배정: 권역별 상위 k곳 점수 합으로 순위 → 하루 한 권역. 후보가 k곳 미만인 권역은 뒤로.
3. 장소 선택: 그 권역에서 점수 순, 같은 이름은 한 번만.
4. 방문 순서: 최고점 장소(출발지 입력 시 출발지에서 가장 가까운 곳)부터 최근접 이웃.
5. 음식·카페(관심사에 있을 때): 그 권역 최고점 1곳씩, 직선 이동거리가 가장 적게 늘어나는 자리에 삽입.
6. 거리는 하버사인 직선거리. 도로망 데이터가 없어 이동시간은 표시하지 않는다(화면 문구 "직선 n km (도로거리·이동시간 아님)").

## 4. 검증과 자기 수정 (`tools/validate.py`, `tools/revise.py`)

검증(코드)이 찾는 위반:

| 유형 | 기준 |
|---|---|
| distance | 하루 직선 이동거리 합 > 60km |
| regions | 하루 방문 권역 수 > 1 (빡빡하게는 2) |
| duplicate | 같은 장소 중복 |
| out_of_scope | 범위 밖(부속섬 등) 장소 |
| count | 장소 수 ≠ k |
| origin | 출발지 → 첫 장소 직선 > 30km |

- 수정은 최대 2회. 행동은 교체(같은 권역 미사용 후보) · 순서 변경 · 제외 중 하나.
- LLM은 위반 목록을 보고 허용 행동만 JSON 스키마로 고른다. 실패·키 없음이면 규칙: 그날 중심에서 가장 먼 장소를 같은 권역 미사용 최고점으로 교체.
- 적용·재검증은 항상 코드. 2회 후에도 남은 위반은 화면에 그대로 보여준다.
- 오류 주입 시연: 1일차에 다른 권역 장소를 끼워 넣으면 검증 실패 → 수정 → 재검증 통과가 실행 로그에 남는다.

## 5. 다시 짜기 — Batch B (`agent/batch_b.py`, `tools/compare.py`)

| 반응 | 처리 |
|---|---|
| 꼭 갈래요 (must) | 항상 고정 |
| 별로예요 (dislike) | 항상 같은 권역 미사용 최고점으로 교체, 대안이 없으면 제외 |
| 좋아요 (interest) | 그 분류에 +0.2 가중으로 다시 점수 → 빈자리 채움 |
| 반응 없음 | LLM(또는 규칙)이 유지·교체를 판단. 위 세 규칙은 항상 우선 |

- 이후 재검증 → 변경 전후 비교(유지·고정·교체·추가·제외 + 이유).
- 게임 속 가상 도착(virtual_arrival)과 반응(feedback)은 따로 저장한다(원칙 5).

## 6. 에이전트 구조와 LLM 판단 지점

- Plan-and-Execute. 필수 단계(조건 검증 → 장소 탐색 → 일정 생성 → 거리 계산 → 검증·수정 → 설명·저장)는 코드가 고정한다.
- 작업 계획(`agent/planner.py`)이 조건에 따라 Tool을 더하거나 뺀다: 음식·카페 탐색, 관심사 필터, 권역 지표 비교(한적함 요청), 월별 지표(월 입력), 출발지 검증(출발지 입력), 입장객 추이(매칭 장소 있을 때), 데이터 품질 점검. 실행 로그에 "추가/생략 + 이유"가 남는다.

| LLM 판단 지점 | LLM이 고르는 것 | 규칙 폴백 |
|---|---|---|
| 조건 해석 | 기간·여유·관심사·이동수단·동행·출발지·월 | 키워드 규칙 |
| 작업 계획 | 추가·생략할 Tool | 조건별 규칙표 (사실과 어긋나는 계획은 코드가 바로잡음) |
| 수정 행동 | 교체·순서·제외 | 가장 먼 장소 교체 |
| 유지·교체 | 반응 없는 장소의 유지·교체 | 반응 규칙 |
| 설명 | 근거 문장 다듬기 | 템플릿 문장 (템플릿에 없는 숫자가 생기면 거부) |

- 모델: 배포는 Upstage Solar Pro 4, 개발 중에는 K-EXAONE 2.5(무료 API). OpenAI 호환 어댑터라 `.env`만 바꾼다. 키·인터넷이 없어도 규칙 기반으로 전 흐름이 돈다.
- 모든 실행에 배치 ID(A-MMDD-HHMMSS / B-…, B는 이전 A와 연결)와 판단 기록(`agent_decisions`: 선택지·선택·주체·근거)이 남는다.

## 7. 한계 (기획서·결과 설명자료에 그대로 기재)

- 1349는 이용자가 입력한 여행 기록이라 같은 장소 반복·비장소 이름이 섞여 있다. 정제 규칙(같은 이름 병합, 좌표 오류 기록 101곳 제외 등)으로 줄였지만 남을 수 있다.
- 분류 없는 장소가 많다(1,459곳/2,688곳, 54%). 관심사 점수가 낮아 일정에 잘 들어가지 않는다.
- 563은 2018~2022 내국인, 1208은 2021 하반기 토요일 렌터카만 반영한다. "현재 혼잡도"가 아니다.
- 입장객 통계(189·190)는 28곳만 매칭되어 점수에 넣지 않고 근거로만 보여준다.
- 거리는 직선이며 도로·대중교통·이동시간을 반영하지 않는다. 이동수단·동행은 표시만 하고 점수에 쓰지 않는다.
- 부속섬은 제외한다.
