## 1. 구현 목표

### 1.1 분석 주제
제주 관광 공공데이터를 바탕으로, 여행자의 한 줄 요청을 해석해 여행 경로를 만들고 스스로 검증·수정하는 AI 에이전트. 사용자가 말 타이핑 게임이나 목록으로 경로를 미리 둘러보며 남긴 반응을 분석해 경로를 다시 설계한다.

### 1.2 AI를 활용한 데이터 분석 목표
- 지역별 방문 수요와 관광 특성을 분석해, 방문이 덜 몰리는 지역도 함께 추천한다(분산형 발견).
- 지역 소비·상권 특성을 분석해 음식점 등 생활형 장소 추천에 반영한다(SHOULD).
- 모든 추천에 사용한 데이터, 기준 시점, 판단 이유를 함께 보여준다.

### 1.3 핵심 원칙
1. 수치는 언제나 Tool(코드) 결과에서만 나온다. LLM은 수치를 만들지 않는다.
2. 사용자가 입력하지 않은 조건은 임의로 채우지 않고 "미반영"으로 둔다.
3. 지역 단위 통계를 개별 장소의 속성으로 표시하지 않는다.
4. 게임과 AI 기능은 강제하지 않는다. 목록 화면에서도 같은 기능을 쓸 수 있다.
5. 게임 속 가상 탐험과 실제 방문 기록은 따로 저장한다.
6. 도로망 데이터 없이는 직선거리를 이동 시간으로 표현하지 않는다.
7. AI는 계획을 보조하고, 최종 선택은 사용자가 한다.

## 2. 서비스 제안

### 2.1 사용자와 운영 시나리오 (D1)
- 운영 형태: 제주빅데이터센터의 체험형 키오스크
- 사용자: 제주 여행을 계획하는 사람(도내 여행을 하는 도민 포함), 관광 데이터를 쉽게 보고 싶은 도민
- 센터 활용 방안: 센터 방문자가 게임이나 대시보드로 관광 데이터를 탐색하고, AI가 분석과 추천 근거를 설명한다.

### 2.2 사용자 흐름

| 단계 | 화면 | 내용 |
| --- | --- | --- |
| 1 | 여행 설명 | 자연어 한 줄 입력. 예: "2박 3일 동안 바다를 보며 여유롭게 쉬고, 현지 음식도 먹고 싶어요" |
| 2 | 조건 확인 | 기간·여유·이동수단·동행·출발지·날짜·관심사를 칩과 선택상자로 보여주고 수정. 빈 항목은 미반영, 기간만 필수 |
| 3 | 경로 만들기 (Batch A) | 목표 해석 → 장소 탐색 → 데이터 분석 → 경로 계획 → 제약 검증 → 필요 시 자율 수정. Tool 실행 로그를 실시간 표시 |
| 4 | 미리보기 | 게임 모드: 경로 순서대로 지명을 타이핑하면 말이 이동, 도착 카드에서 관심·꼭 갈래요·별로예요 표시. 목록 모드: 같은 버튼을 장소 카드에서 사용 |
| 5 | 다시 짜기 (Batch B) | 피드백 분석 → 유지·교체 판단 → 대체 장소 탐색 → 경로 수정 → 재검증 |
| 6 | 최종 계획 | 개인화된 경로, 장소별 추천 근거, 변경 전후 비교(유지·고정·교체·추가·제외), 인쇄 |

### 2.3 핵심 기능
- 한 줄 요청 해석과 부족한 조건 식별
- 공공데이터 기반 장소 탐색과 지역 분석
- 일정 생성과 제약 검증, 검증 실패 시 자율 수정
- 메트로타이핑식 경로 퀘스트(지명 타이핑으로 말 이동)
- 탐색 반응 기반 선호 분석과 경로 재설계
- 추천 근거 패널(장소 정보와 지역 지표 분리 표시, 데이터 출처, 기준 시점, 대안 장소)

### 2.4 편의성
- 필수 입력은 기간 하나. 나머지는 선택.
- 게임이 어려운 사용자는 목록 모드로 같은 작업을 한다.
- AI 연결이 끊겨도 규칙 기반 모드로 핵심 기능이 동작한다.
- 대기 중에는 에이전트가 무엇을 하는지 로그로 보여준다.

### 2.5 차별점
- 메트로타이핑의 "노선을 따라 역 이름을 치는" 방식을 여행 경로 미리보기에 적용
- 방문 집중도 데이터를 활용한 분산형 추천
- 에이전트의 검증 실패와 자기 수정 과정을 화면에서 그대로 보여줌

## 3. Agent 개발 구성

### 3.1 역할 분리

| 구성 요소 | 책임 |
| --- | --- |
| AI Agent | 목표 해석, 작업 순서 판단, 도구 선택, 오류 대응, 계획 수정, 설명 생성 |
| Deterministic Tools | 데이터 조회, 통계 계산, 거리 산출, 일정 검증, 결과 비교, 상태 저장 |
| Game Engine | 말 이동, 타이핑 판정, 지도 탐색, 장소 콘텐츠 표시, 행동 이벤트 수집 |
| Dashboard | 관광 데이터 시각화, 경로 비교, 추천 근거, 에이전트 실행 결과 확인 |

게임 엔진의 타이핑 판정과 지도 렌더링은 에이전트가 담당하지 않는다. 에이전트에는 의미 있는 탐색·선택·거부 이력만 전달한다.

### 3.2 실행 방식: Plan-and-Execute
- 파이프라인 골격은 코드로 고정한다.
- LLM은 허용된 선택지 안에서만 판단하고, 결과는 JSON 스키마로 강제한다.
- 반드시 거쳐야 하는 단계(데이터 품질 확인, 일정 검증)는 코드가 끼워 넣는다.
- 목표에 따라 실행하는 Tool이 달라진다. 예: 음식 취향이 있으면 상권 분석을 추가한다.

### 3.3 Workflow

```
Batch A — 최초 경로 생성
  [M1 목표 해석]* → [M2 작업 계획]* → [M3 데이터 조회] → [M4 분석·품질]
  → [M5 일정 생성] → [M6 검증·수정]* (위반 시 수정, 최대 2회) → [M8 설명·저장]*
                                  │
                     게임·목록 미리보기 (관심·꼭 갈래요·별로예요)
                                  │
Batch B — 탐험 후 재설계
  [피드백 수집] → [M7 유지·교체]* → [M3·M4 재조회·분석] → [M6 재검증·수정]*
  → [M7 경로 Diff] → [M8 설명·저장]*

  * = LLM 판단 지점 (실패 시 규칙 기반 정책으로 대체)
```

### 3.4 모듈과 Tool

17개 Tool을 8개 내부 모듈로 묶는다.

| 모듈 | 포함 Tool | 우선순위 | 구현 |
| --- | --- | --- | --- |
| M1 목표 | `parse_travel_goal`, `validate_goal` | P0 | LLM 구조화 출력 + 코드 검증 |
| M2 계획 | `plan_tasks` (신규) | P0 | LLM이 허용 목록에서 도구·파라미터 선택, 필수 단계는 코드가 강제 |
| M3 조회 | `search_places`, `get_region_data` | P0 | SQL |
| M4 분석 | `analyze_tourism`, `check_data_quality` | P0 | 코드 |
| M4 분석 | `analyze_commerce` | P1 | 코드 |
| M5 일정 | `calculate_route`, `create_itinerary` | P0 | 코드 (일자별 권역 묶기 + 방문 순서) |
| M6 검증·수정 | `validate_itinerary`, `revise_itinerary` | P0 | 위반 목록은 코드, 수정 행동 선택은 LLM, 적용은 코드 |
| M7 재설계 | `analyze_feedback`, `compare_itineraries` | P0 | 코드 집계 + LLM 유지·교체 판단 |
| M8 출력·상태 | `generate_quests`, `explain_decisions`, `export_travel_plan`, `save_agent_state` | P0 | 코드 + 템플릿, LLM은 문장만 다듬음 |

`calculate_route`는 로컬 도로망이나 검증된 이동 데이터가 없으면 직선거리 기반 검증으로 범위를 줄인다(5.4 참고).

### 3.5 LLM 판단 지점과 폴백

| 판단 지점 | LLM이 고르는 것 | 규칙 기반 폴백 |
| --- | --- | --- |
| 목표 해석 | 기간·관심사·여유·이동수단·동행·출발지 추출 | 키워드 규칙 추출 |
| 작업 계획 | 실행할 Tool과 파라미터 | 관심사별 고정 규칙표 |
| 수정 행동 선택 | 위반 목록에 대한 수정 방법(교체·순서 변경·제외) | 가장 먼 장소를 같은 권역 후보로 교체 |
| 유지·교체 판단 | 피드백을 근거로 유지·고정·교체·추가 | 꼭 갈래요=고정, 별로예요=교체, 선호 카테고리 점수 상위=추가 |
| 설명 생성 | 근거 데이터를 문장으로 정리 | 템플릿 문장 |

### 3.6 판단 및 자율 수행 범위
- 할 수 있는 것: 허용 목록 안의 Tool 선택과 파라미터 결정, 후보 부족 시 검색 범위 조정, 검증 실패 시 수정 행동 선택, 피드백 기반 재설계, 근거 데이터가 부족하면 "근거 부족"으로 보고
- 할 수 없는 것: 데이터베이스 직접 수정(저장은 `save_agent_state`만), 외부 프로그램 실행, 수치 생성, 허용 목록 밖의 행동
- 반복 제한: 검증-수정 루프 최대 2회. 이후에도 위반이 남으면 위반 내용을 표시하고 사용자에게 넘긴다.

### 3.7 상태와 실행 기록
- 모든 실행에 배치 ID를 붙인다(예: `A-1116-193916`, `B-…`). Batch B는 이전 Batch A ID와 연결한다.
- `agent_decisions`에 입력 상태, 선택지, 선택 결과, 선택 주체(LLM/규칙), 근거, Tool 호출 결과를 기록한다.
- 사용자 이벤트는 타입을 나눠 저장한다: `virtual_arrival`(가상 도착), `feedback`(관심·꼭 갈래요·별로예요), `itinerary_add`, `visited`(실제 방문).
- 재현성 정의: "같은 프로필 + 같은 상호작용 이력 + 같은 데이터셋 버전 + 같은 설정"이면 같은 순위가 나온다. 재현성 테스트는 코드가 만든 순위로 하고, LLM 문장은 대상에서 제외한다.

## 4. 데이터 활용 계획

### 4.1 필수 데이터 (D3, 미정)
- 대회 조건: 제주데이터허브 공개 데이터 또는 제주빅데이터센터 방문 제공 데이터 중 1종 이상
- 선정 목표: 지역 단위 방문·소비 통계 1종 + 장소 목록 1종
- 확인할 것: 장소 좌표 유무, 업체 단위 데이터 여부, 통계의 공간 단위(읍면동/시군 등)와 기간 단위
- 장소 데이터가 허브에 없으면 적법한 외부 공개 데이터로 보완하되, 분석의 핵심은 허브 데이터로 유지한다.

실제 원본 데이터를 확인하기 전까지 컬럼과 수치는 확정하지 않는다.

### 4.2 검토할 데이터 분야
제주 지역별 관광객 방문 통계, 관광지·명소 정보, 지역별 소비 데이터, 관광지·상권별 업종 분포, 음식점·카페 정보, 지역별 위치·공간 데이터, 관광 관련 시간 변화 데이터

### 4.3 수집·전처리 절차
1. 원본 데이터 수집과 버전 관리
2. 지역명 표준화
3. 읍면동과 관광지 매핑(좌표 → 읍면동)
4. 좌표계와 공간 단위 정규화
5. 기간 정규화와 월별 기준 통일
6. 중복 검사
7. 결측치·이상치 확인
8. 수치와 데이터 타입 검증
9. 통계 지표 계산
10. 데이터 품질·출처 메타데이터 생성

### 4.4 Agent용 분석 데이터셋 최소 필드
관광지 ID, 지역 ID, 장소 카테고리, 좌표, 통계 기간, 측정값, 데이터 출처, 데이터 갱신일, 품질·신뢰 상태

### 4.5 데이터베이스 (SQLite, 테이블 후보)

| 테이블 | 목적 |
| --- | --- |
| regions | 지역·행정구역 |
| places | 관광지·음식점·카페 등 장소 |
| tourism_stats | 지역별 관광 통계 |
| commerce_stats | 지역별 소비·상권 데이터 |
| data_sources | 원본 출처와 품질 정보 |
| user_profiles | 사용자 취향과 기본 여행 조건 |
| user_interactions | 탐색과 피드백 이력(이벤트 타입 구분) |
| itineraries | 여행 일정과 방문 예정 장소 |
| agent_decisions | 에이전트 판단과 실행 기록 |

정규화 수준은 실제 데이터 스키마를 확인한 뒤 정한다.

### 4.6 이용조건
- 참가자용 데이터 목록 파일은 외부 배포·제3자 제공·GitHub 업로드 금지. 저장소를 공개하면 제외한다.
- 데이터허브 API 키는 제출물에 넣지 않고, 발급·설정 방법을 매뉴얼에 적는다.
- 가공 데이터(SQLite)를 제출물에 넣어도 되는지는 데이터 이용조건에서 확인한다.

## 5. 개발·탑재 계획

### 5.1 구현 범위

**MUST** (11/19 밤 1차 제출본에 모두 동작)
- 필수 데이터 기반 SQLite와 출처·기준 시점 메타데이터
- Batch A/B 전체 흐름과 실행 로그(배치 ID)
- 검증 → 수정 루프와 오류 주입 시연
- 대시보드: 한 줄 입력, 확인 칩, 일정, 근거 카드, 통계 차트 1~2개, 실행 로그, Diff
- 게임: 경로 퀘스트 타이핑, 도착 카드, 관심·꼭 갈래요·별로예요
- Solar Pro 4 연동과 규칙 기반 폴백(LLM 없이도 동작)
- 설치 스크립트, README, 테스트 프로필 3종, 테스트 10종

**SHOULD**
- `analyze_commerce`(상권·업종 분석)
- OSM 도로망으로 장소 간 도로거리 사전 계산("도로거리 기반 추정"으로 표시)
- PDF 저장, 일정 요약을 담은 QR
- 다양성 보정(점수가 비슷할 때 카테고리·지역 분산)
- 로컬 LLM 오프라인 모드

**WON'T**: 멀티플레이, 3D, 실시간 데이터, 모바일 앱, 계정

### 5.3 센터 실행환경과 외부 서비스 의존성 (D7)
- 센터 PC 최소사양: Intel Core i7-8700 / GTX 1060 / RAM 32GB / VRAM 3GB
- 실행 모드: 인터넷 연결 시 API 모드(Solar Pro 4), 끊기거나 API가 실패하면 규칙 기반 모드로 핵심 기능 유지
- 외부 의존성: Upstage API(인터넷 필요). 그 외 데이터·지도·정적 파일은 모두 로컬
- 평가용 키: 대회 전용 키 발급, 사용 한도 설정, ZIP의 실행환경·매뉴얼에 포함, 평가 종료 후 폐기
- 개인정보: 여행 요청 문장과 Tool 결과 요약만 전송. 화면에 외부 전송 안내. API 로깅 동의는 하지 않음
- 글꼴: 키오스크 배포 시 글꼴 파일을 함께 넣는다(오프라인에서도 같은 화면 유지)

### 5.4 이동 검증 정책
- P0: 하루 직선 이동거리 합계 상한(설정값 60km)과 하루 방문 권역 수로 검증
- 직선거리는 "직선 n km, 도로 거리나 이동 시간이 아님"으로 표시
- 출발지를 입력하지 않으면 숙소에서의 거리는 검증하지 않는다

## 6. 검증 계획

### 6.1 테스트 10종
1. 취향이 바뀌면 추천 결과가 바뀌는가
2. 같은 조건에서 같은 결과가 나오는가
3. 추천을 거부하면 적절한 대안을 주는가
4. 데이터셋 지표가 바뀌면 추천에 반영되는가
5. 필수 데이터가 빠졌을 때 안전하게 처리하는가
6. LLM 실행에 실패해도 핵심 서비스가 동작하는가
7. 인터넷을 끊어도 필수 기능이 동작하는가(규칙 기반 모드)
8. 게임과 대시보드에서 같은 분석 결과가 나오는가
9. 데이터 출처와 기준 시점을 확인할 수 있는가
10. 가상 탐험 기록과 실제 방문 기록을 구분하는가

### 6.2 테스트 프로필 3종
- "2박 3일 동안 바다를 보며 여유롭게 쉬고, 현지 음식도 먹고 싶어요"
- "아이와 함께 1박 2일, 렌터카로 오름이랑 체험 위주로 다니고 싶어요"
- "혼자 3박 4일, 버스로 조용한 동네와 카페를 천천히 보고 싶어요"

### 6.3 오류 주입 시연
초안에 다른 권역의 장소(예: 서부 일정 중 성산일출봉)를 넣어 하루 이동거리 초과를 일으키고, 에이전트가 이를 탐지해 같은 권역 장소로 교체하는 과정을 로그로 보여준다.
