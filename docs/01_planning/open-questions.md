## 2. 기획 빈틈 (v0을 읽고 정리한 것. brainstorming에서 하나씩 확인)

데이터·에이전트
- [x] **장소 점수 공식이 없다.** → 설계 문서 6.2. `search_places`가 후보를 어떤 지표로 순위 매기는지(관심사 일치, 방문 집중도, 거리) 정의 필요. 재현성 테스트(같은 조건 → 같은 순위)의 전제.
- [x] **"방문이 덜 몰리는 지역" 지표의 원천 데이터가 정해지지 않았다.** → 563 읍면동 방문/거주 비율 + 1208 장소 반경 혼잡 (설계 문서 5.1, 6.2). D3과 함께 결정. 지역 단위 통계면 원칙 3(지역 지표 ≠ 장소 속성)에 따라 화면에서 분리 표시.
- [x] **권역 정의가 없다.** → 5권역 (설계 문서 5.3). M5 "일자별 권역 묶기", 5.4 "하루 방문 권역 수", 6.3 "서부 일정 중 성산일출봉" 모두 권역 경계가 필요. D4와 함께 결정(예: 동·서·남·북·제주시내 5권역, 읍면 단위 묶음).
- [x] 하루 방문 장소 수 기준 → 여유롭게 3 / 보통 4 / 빡빡하게 5 (설계 문서 6.3).(여유도 '여유롭게/보통/빡빡하게'와 연결?)과 일정 시간 슬롯 유무.
- [x] 음식점 추천이 SHOULD → TourAPI 음식점 분류로 하루 1곳, 근거는 '등록 음식점'만 (설계 문서 6.3).(analyze_commerce)인데, 테스트 프로필 1은 "현지 음식도 먹고 싶어요". MUST 범위에서 음식 요청을 어떻게 처리할지(미반영 표시? 장소 카테고리로만?).
- [x] 장소별 지명 타이핑에 쓸 표기 → 빌더 판단, 규칙만 정함 (설계 문서 6.9).(정식명/약칭), 긴 이름 처리.

## 3. 리스크 (기획문서_v0 9장 + 추가)

| 리스크 | 대응 |
|---|---|
| 장소 데이터(이름·좌표)가 허브에 없음 | 허브에 좌표 있는 장소 데이터가 있음(1349, 811 등, data-selection.md). 원본 확인 후 판단. 부족하면 적법한 외부 공개 데이터로 보완 |
| 관광지별 방문 통계의 관광지명이 장소 목록 이름과 안 맞음 | 매칭표를 수작업으로 만들 범위를 D4로 제한 |
| 후보 데이터가 meta-only라 실제 기간·컬럼이 다를 수 있음 | 11/16 중 원본 확인. 안 맞으면 차순위 후보로 |
| 지역 통계를 개별 장소 속성으로 오해 | 화면과 점수에서 지역 지표로 분리 |
| 에이전트 응답 지연 | 수정 루프 최대 2회, 대기 중 로그 스트리밍 |
| API 장애·한도 초과 | 규칙 기반 폴백으로 자동 전환 |
| 입력 문장이 모호함 | 확인 칩 화면, 미입력 항목은 미반영 |
| UI 프로토타입의 하드코딩 수치가 그대로 구현에 남음 | design/ui-prototype/README.md 목록대로 Tool 결과로 대체 |
| 외부 CDN 의존으로 센터 PC 오프라인 시 화면 깨짐 | 빌드 시 Tailwind·글꼴·아이콘·이미지 로컬화 |
| 데이터 목록 파일 유출 | 저장소 private, .gitignore |
